We are starting implementation of SPACE WARS Phase 1.

This is NOT a backend phase.

The purpose of this phase is to build a polished, locally playable VISUAL PROTOTYPE of the Space Wars browser game so I can decide whether the core galaxy-map concept actually looks and feels good enough to continue developing.

I care much more about:

- visual quality
- galaxy presentation
- map interaction
- territory
- movement
- atmosphere
- information hierarchy
- satisfying interactions

than I do about production architecture right now.

DO NOT turn this into another architecture/documentation exercise.

BUILD THE PROTOTYPE.

==================================================
PRIMARY GOAL
==================================================

When I run:

npm install
npm run dev

I want to open Space Wars in my browser and immediately see something that resembles a REAL polished browser strategy game.

I want the prototype to answer this question:

"Do I enjoy looking at, navigating and interacting with this galaxy enough that I want to build the real game?"

The dashboard/map must therefore look substantially more polished than an engineering wireframe.

Do not stop at plain cards, basic HTML controls, circles connected by lines or generic developer styling.

VISUAL QUALITY IS AN ACCEPTANCE REQUIREMENT.

Spend substantial effort on:
- map composition
- visual hierarchy
- territories
- planets
- fleet motion
- interaction feedback
- dashboard density
- sci-fi styling
- polish

Use the existing concept image/design direction from our project as the visual north star:

A dark premium sci-fi strategic dashboard with:
- central galaxy map
- territory regions
- planets
- asteroids
- fleet routes
- side panels
- resources
- production
- live events

Do not reproduce concept art pixel-for-pixel.

Build a practical implementation with the same feeling.

Do not over-engineer the repository.

==================================================
GALAXY GENERATION
==================================================

Create a deterministic seeded demo galaxy.

The SAME seed must generate the SAME galaxy.

Initial target:

- roughly 140–180 systems
- roughly 30–40 commanders/empires
- multiple civilizations
- planets
- asteroid fields
- connected travel lanes
- fleets
- mining locations
- neutral frontier territory

Adjust numbers if necessary for readability/performance, but the world should feel LARGE.

This should not look like a small 15-node tech tree.

I should be able to pan around and discover different regions.

Provide an easy developer control for:

- current seed
- regenerate galaxy
- reset demo
- pause/resume simulated activity
- optionally speed up local simulation

==================================================
TERRITORY
==================================================

Territory rendering is one of the MOST IMPORTANT visual requirements.

I want to immediately understand:

- this is my empire
- this belongs to another player
- this belongs to another civilization
- this is neutral frontier
- this is a contested/border region

DO NOT simply put a giant circle behind every owned system.

Generate convincing strategic territory shapes from controlled systems.

Possible approaches include:
- Voronoi-style regions
- smoothed hulls
- influence fields
- merged SVG polygons
- another appropriate geometry technique

Use transparent/subtle fills and stronger border/frontline emphasis.

Territory should not hide the map underneath it.

When ownership changes after a local attack, the territory visualization must visibly update.

That ownership-change effect is one of the key things I want to evaluate.

==================================================
FLEET MOVEMENT
==================================================

Fleet movement must actually work locally.

User flow:

1. Select owned fleet.
2. Select destination.
3. Choose MOVE / ATTACK / MINE depending on target.
4. Show route.
5. Show estimated travel time.
6. Confirm.
7. Fleet icon visibly moves along the route.
8. ETA counts down.
9. Arrival changes local state.

For prototype testing use fast movement:

approximately 15–60 seconds depending on route.

Do not use final production timing.

Movement should interpolate smoothly.

It should not teleport from node to node.

For multi-edge routes, visually travel along the complete route.

==================================================
ROUTES
==================================================

When a fleet is selected/moving:

- emphasize its route
- show direction
- use a restrained animated/dashed travel treatment
- distinguish player route from enemy activity

Do not animate every lane constantly.

The map should remain readable.

==================================================
LOCAL ATTACK / CAPTURE
==================================================

Implement a TEMPORARY MOCK combat/capture interaction.

This is NOT the final Battle Lab V2 integration.

Do not spend this phase extracting the full combat engine unless it is trivial after the dashboard is complete.

Flow:

1. Select hostile/neutral system.
2. Click ATTACK.
3. Select available player fleet.
4. Show:
   - fleet power
   - enemy estimated power
   - travel time
5. Launch.
6. Fleet visibly travels.
7. On arrival resolve using simple seeded prototype logic.
8. Display result.
9. If victory:
   - change owner
   - update map
   - change territory region
   - update selected panel
   - add event
   - optionally show small victory notification

Example temporary calculation:

attacker power
vs
defender power
plus bounded deterministic seed variation

Keep this isolated in clearly named mock/demo logic.

We will replace it later.

The important thing is that CAPTURING TERRITORY SHOULD FEEL SATISFYING.

==================================================

Before considering Phase 1 complete, manually run the app and verify that a player can:

1. Open the dashboard.
2. Immediately understand their territory.
3. Pan around a substantial galaxy.
4. Zoom in and out smoothly.
5. Inspect their own system.
6. Inspect a rival system.
7. Inspect an asteroid.
8. Select one of their fleets.
9. Send it somewhere.
10. Watch it move.
11. Attack a neutral/hostile target.
12. See conquest change ownership/territory.
13. Send a mining fleet.
14. Receive mined resources.
15. Build a ship.
16. See the completed ship reflected in local state.
17. Watch rival fleets/world events occur without player input.
18. Read and interact with the event log.
19. Change the demo seed and see a different believable galaxy.
20. Reset the prototype.

Most importantly:

Stand back and assess whether it looks like a credible browser strategy game rather than a software demo.

If it does not, continue polishing before declaring completion.
